# Day Planner: Design

Date: 2026-10-08
Status: Draft v2 for user review (scope widened from study-only to an everyday planner)

## Purpose

A personal everyday planner. The user juggles university, volunteer meetings, work, paid private lessons, plus gym, chores, errands, social plans and personal projects. Their schedule changes every semester and sometimes every month. The tool fits flexible tasks around fixed commitments, ramps up toward deadlines, and stays usable by other people later (nothing about one person's schedule is hard-coded). Studying is the main flexible task, and it has the deepest logic (course workload and exam deadlines), but it is one kind of task among several.

## Success criteria

- The user can enter their schedule once as recurring patterns and update it cheaply when a semester or month changes.
- Given courses, tasks and deadlines, the tool produces a week plan of task blocks in free time.
- Time for anything with a due date rises as the date approaches, and the tool says plainly when a deadline cannot be met.
- Plans respect the user's personal rules (see Preferences).
- Re-planning after a change never rewrites past days or touches real commitments.

## Scope and phasing

Built in this order. Each phase is useful on its own and can be a stopping point.

1. **Core planner:** own schedule entry, tasks (all categories), courses, deadlines, preferences, block generation.
2. **AI workload estimate:** suggested weekly hours per course from basics, and optionally a syllabus.
3. **Commute:** per-event travel time via Google Maps (also used by errands and any task with a place).
4. **Check-in:** daily "how are you feeling" that shrinks the day's plan when the user is low, plus a short motivational nudge.
5. **Class-attendance advice:** suggestion, with reasons, on whether a class is worth attending. Needs a syllabus. Advisory only; the user decides.
6. **Optional later:** Google Calendar import, accounts for other users, phone access via hosting.

## Architecture

A web UI in the browser talks to a small local server running on the user's machine. The server calls two external services (AI, Google Maps) and holds their keys. Data is stored locally (file or SQLite). No Google sign-in is needed in v1.

Components, each with one purpose:

- **Schedule store:** places, commitments, tasks, courses, deadlines, preferences, check-ins.
- **Planner:** pure logic, no AI. Inputs: commitments, tasks, target hours, deadlines, preferences. Output: task blocks and warnings.
- **Workload estimator:** AI call. Input: course basics and optional syllabus text. Output: suggested weekly hours with a short explanation. The user can override the number.
- **Commute resolver:** Maps call. Input: two addresses and a travel mode. Output: travel time plus a safety margin.
- **Web UI:** see the UI section. Not designed yet.

The AI only estimates hours. The planner does all scheduling, so plans are reproducible and testable, and the AI can be turned off without breaking the planner.

## Data model

- **Place:** name, address (home, campus, church, gym, a student's home).
- **Commitment:** something fixed in time. Title, place, time pattern, category. A time pattern is a one-off, or a recurring weekly pattern with start and end dates, for example "Chemistry lecture, Tue and Thu 10:00, Sept to Dec". A new semester means ending old patterns and adding new ones.
- **Task:** something that needs time but not a fixed slot. Title, category, duration or weekly target, optional place, optional due date, priority. Examples: "Gym, 3 sessions per week", "Laundry, 1 hour per week", "Pick up parcel, errand, by Friday", "Side project, 4 hours per week".
- **Course:** name, credits, difficulty rating, optional syllabus text, estimated weekly hours (AI suggestion, user override). A course produces study tasks.
- **Deadline:** attached to a course or a task. Kind (exam, assignment, other), due date, weight.
- **Preferences:** allowed hours per day type, days-off cutoff, max block length, minimum break, protected times.
- **Block:** generated by the planner and stored separately from commitments, so re-planning never touches real commitments.
- **Check-in:** date and reported state (used from phase 4).

### Categories

Commitment and task categories start as: university class, study, work, private lesson, volunteering, mass, gym/exercise, chores, errands, social, personal project. The user can add their own. Categories drive defaults (typical block length, whether the item is soft) and let the plan be filtered and balanced by area of life.

## Planner behavior

1. **Inputs:** commitments (with travel blocks), tasks, target weekly hours, deadlines, preferences.
2. **Free slots:** each day's allowed window minus commitments and travel.
3. **Demand:** each task and course starts at its weekly target or required duration. Demand ramps up as a due date nears (an exam in 10 days asks for more than the same exam in 30).
4. **Fill:** assign each slot to the item with the most unmet demand, weighted by priority. Blocks respect the max length. The same item is not scheduled back-to-back for too long. Errands are grouped by location where possible, and recurring targets like gym are spread across the week.
5. **Flag problems:** if free time cannot cover a deadline's demand, report it explicitly (for example "Chemistry exam is short by 6h"). Never silently drop it.
6. **Re-plan:** on any change, rerun from today forward. Past days are never rewritten.

### When time is short (default priority order)

1. Fixed commitments (classes, work, lessons, mass, meetings) are never moved.
2. Items with an approaching deadline.
3. Recurring health items (gym), reduced before being dropped.
4. Chores and errands without a due date.
5. Personal projects.
6. Soft social time is protected until a deadline would be missed (see below).

This is a default for the user to confirm or reorder. Whenever the planner drops or reduces something, it says what and why.

### Personal rules (initial preferences)

- **Sunday 8pm mass** is a protected recurring block with a short travel buffer. Nothing is scheduled over it.
- **Weekend outings:** Friday and Saturday evenings are soft-free. The planner avoids them. Study may use them as a last resort, when a deadline would otherwise be missed or a weekly study target would fall short, and then the plan says so. Other categories (chores, gym, errands, projects) never take them.
- **Days off:** an earlier cutoff than on weekdays, set by the user.
- **Private lessons** are fixed paid work. Other items move around them, and they are never the thing dropped when a deadline is tight. A cancelled or moved lesson frees its slot, travel included, and triggers a re-plan.

## Commute

- Each commitment or task with a place resolves a location in this order:
  1. Its own place or address.
  2. A saved place matched by name in the title (for example a student's name). If a name matches nothing, the tool asks for the address once and remembers it.
  3. If still unknown, a default travel allowance set by the user, and the item is flagged "address missing".
- Travel time comes from Google Maps for the user's travel mode (walking, transit or driving), plus a safety margin because times vary with traffic.
- Maps is a separate Google service from Calendar. It needs its own API key and billing enabled on a Google Cloud project. The free monthly credit should cover personal use, and this must be verified before relying on it.
- If Maps is unavailable, the default allowance is used and the user is told.

## Check-in (phase 4)

A daily prompt on how the user feels. If low, the planner shrinks that day's plan to a user-chosen minimum, moves the remainder to the next suitable day, and shows a short nudge. Replanning is plain logic. Only the wording of the nudge may be AI-written.

## Class-attendance advice (phase 5)

For courses with a syllabus, the tool suggests whether a class is worth attending based on the evidence: attendance weight, whether lectures are recorded, how much of the grade depends on it, and how far behind the user is. It presents the suggestion and its reasons. It never decides for the user.

## Error handling

- AI unavailable: the planner uses the user's own hour numbers, and the tool says so.
- Maps unavailable: default travel allowance is used, and the tool says so.
- Unmeetable deadlines and missing addresses are surfaced as visible warnings, not hidden.

## Testing

- The planner is tested heavily with example weeks: Sunday mass, a deadline that cannot be met, a cancelled lesson, a low check-in day, gym spread across a busy week, errands grouped by location.
- The AI and Maps components are tested with fake responses.

## UI

**Pending the user's references.** No screen, layout, colors or interaction is designed here, and none should be invented. The UI section will be written from the references the user provides (screenshots, links, sketches, or notes on what they like). Capabilities the UI must expose, whatever it looks like: a week view of commitments plus generated blocks, management of commitments, tasks, courses and deadlines, preferences, a visible warnings/behind-schedule indicator, and later the daily check-in.
