# doitwithme UI v1: Design

Date: 2026-10-09
Status: Draft for user review
Builds on: `2026-10-08-study-planner-design.md` (planner) and the Phase 1 code on branch `phase-1-core-planner`.

## Purpose

A bold, simple, functional web UI for the planner, for one person on their own machine. It shows the week, lets them manage commitments, tasks and deadlines without editing JSON, and gives the planner a voice through a small assistant character, Nudge, who delivers warnings and asks permission before using protected time.

## The visual source of truth

The approved design is **board D, "A+. Vermilion, with categories"** on the private canvas https://claude.ai/artifact/TNMnuzerDogRwvQxJSNdPP (file `project/D.dc.html`). The UI must reproduce it. The other screens (F Day, G Deadlines, H Setup, I First run, J Nudge states) follow the same tokens and are pending approval. Nothing visual is invented beyond it: anything the board does not show (the Day, Deadlines and setup screens, empty and error states) is built from the board's own tokens and patterns and shown to the user for approval before it is final.

Rules the user set, binding on every screen:
- Bold, high design, simple, functional. No emojis anywhere. No gradients, no purple, no sparkle or "AI" iconography.
- Color carries meaning but is never the only signal: every block also carries a text label.
- Pictures may come later but never appear on the calendar itself.
- Nudge is an original character (flat-bottomed arch, two vertical bar eyes, notification badge). It is not a copy of any other artist's character.

### Design tokens (from board D)

| Token | Value | Use |
|---|---|---|
| paper | `#F1EEE6` | page ground |
| ink | `#111111` | text, fixed blocks, rules |
| study | `#FF4B1F` | study blocks, primary action, Nudge body |
| gym | `#1746F0` | gym blocks (white text) |
| admin | `#F5B400` | chores and errands |
| outline | 2px ink border, no fill | projects, social, unknown categories |
| muted | `#6F6B61` | secondary text |

Type: **Bricolage Grotesque** (400, 600, 800) for display and body, **DM Mono** (400, 500) for labels, times and counts. Corners are square. The page title is 236 px weight 800 with letter-spacing -0.06em; day numbers are 40 px weight 800; mono labels are 12 px uppercase with 0.06em tracking.

All colors, fonts and sizes live in one stylesheet of CSS custom properties (`public/css/tokens.css`). Components only reference tokens. A later dark theme is then a second set of token values under `[data-theme="dark"]`, with no component changes. Dark mode itself is out of scope now.

Fonts are self-hosted (`public/fonts/`, woff2, both OFL-licensed) so the app works offline and sends nothing to third parties. If a font fails to load, system sans and monospace are used.

### Category mapping

- A **commitment** (anything fixed in time) is drawn as a black block, labelled with its category in uppercase: CLASS, LESSON, MASS, WORK, and so on.
- A **task block** takes its color from the task category: `study` is vermilion, `gym` is cobalt, `chores` and `errands` are mustard, everything else (`personal project`, `social`, custom categories) is outlined. The label is the category.
- The legend is a **Show** filter list with the week's count per group: Fixed, Study, Gym, Chores and errands, Projects and social.

## Scope of UI v1

**In:**
1. **Week screen**, as board D: giant "Week NN" (ISO week number), date range, "N needs you" count, seven day columns, blocks sorted by start time, a "Booked" total per day (fixed plus planned minutes), previous and next week arrows, a Today button, the Show filters, and Nudge.
2. **Day screen**: one day, larger blocks, same data and filters.
3. **Deadlines screen**: each deadline with due date, effort needed, minutes planned, minutes short, in the same visual language. Shortfalls are shown in vermilion.
4. **Setup screens** for commitments (one-off or weekly with weekdays and date range, cancelled dates, buffer before), tasks (category, weekly minutes, max block, one session per day, priority 1 to 5), deadlines, and preferences (day windows, days off, minimum block and break, soft windows, soft-time mode).
5. **Replan** button, and an automatic replan after any setup save.
6. **Nudge**: speaks the planner's warnings, with real buttons (see Behavior).
7. **First run**: when there is no data, a plain empty state with a "Load the example" button that fills in the example schedule.
8. **Menu with Jump to search**, driven by the section registry (see Navigation and room to grow).
9. **Settings screen** with the initial groups Appearance, Notifications and Planner, built on the declarative row pattern.

**Out (later):** pictures and the cover-image slot, the AI chat behind "Ask me", Maps commute, daily check-in, dark theme, phone layout beyond a basic stacked fallback, Google Calendar import.

## Architecture

- **No framework, no build step, no npm dependencies.** Plain HTML, CSS and ES modules in `public/`, served by the existing local server (`127.0.0.1` only). The disk is nearly full, so this is a hard constraint.
- The **planner stays the only source of truth.** The UI never schedules anything; it draws what the API returns.
- **Hash routing** (`#/week/2026-10-12`, `#/day/2026-10-14`, `#/deadlines`, `#/setup/commitments`, and so on). The selected week is in the URL, so back and forward work and a week can be bookmarked.
- **Files** (each one purpose): `index.html`; `css/tokens.css`, `css/app.css`; `js/api.js` (fetch wrapper); `js/model.js` (pure view-model functions: group by day, totals, filter, counts, ISO week, category mapping, Nudge message building, section search); `js/router.js`; `js/sections.js` (the registry); `js/menu.js`; `js/views/week.js`, `day.js`, `deadlines.js`, `setup.js`, `settings.js`; `js/nudge.js`; `js/dom.js` (small element helper).
- **Rendering** builds elements with `textContent`, never `innerHTML` with data, so user text can never inject markup.
- **Persisted per-viewer UI choices** (selected filters, opted-in notifications) go in `localStorage`, wrapped in try/catch, and the UI works without it.

### Navigation and room to grow

The app will keep gaining options (AI and Nudge settings, commute, check-in, themes, pictures, integrations), so navigation must scale without redesign.

- **Section registry** (`js/sections.js`): the single list of everything the app offers. Each entry has `id`, `title`, `group` (`views`, `setup`, `settings`, `connections`), `route`, `description` and a `render` function. The top tabs, the Menu and the Jump-to search are all generated from it. Adding a feature means registering one section; no navigation code changes. Only registered (built) sections ever appear.
- **Menu** (`js/menu.js`): a **Menu** button in the top bar opens a full-screen overlay (board K) listing the groups with large type and the current section highlighted. The **Jump to** field filters sections as you type; `/` opens the menu with that field focused, Esc closes it, Enter opens the first match. Focus is trapped while open and returned to the button on close.
- **Top tabs** show only the four everyday views (Day, Week, Deadlines, Setup). Everything else lives in the Menu.
- **Settings pattern** (board L, `js/views/settings.js`): a settings screen is a list of groups; each group is a list of rows; each row has a title, a one-sentence description and a control (segmented choice, toggle or select). Rows are declared as data (`{ id, group, title, description, control, read, write }`) so a new option is one declared row. A control that is not available yet is shown disabled with a "Later" tag.
- **Initial settings groups:** Appearance (theme: Light now, Dark disabled and marked Later), Notifications (system notifications on or off), Planner (soft time: Ask first or Automatic). Later groups (Nudge and AI, Commute, Check-in) slot in the same way.
- **Connections group** exists for integrations; in v1 nothing is registered in it, so it does not appear in the menu. Board K shows it dimmed only as a preview of how future sections look.

### Server changes

- **Static files:** `GET` and `HEAD` for paths under `public/` only. The path is normalized and anything resolving outside `public/` is refused (404). Known content types only. `Cache-Control: no-store` during development. The existing Host-header allowlist still applies.
- **Security headers:** `Content-Security-Policy: default-src 'self'; img-src 'self' data:; frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- **`GET /api/example`:** returns the validated example state (`examples/sample-state.json`) without saving it. The UI then saves it through the normal `PUT /api/state` when the user accepts.
- The existing API (`GET`/`PUT /api/state`, `POST /api/replan`) is unchanged except for the planner changes below.

## Server endpoints for Nudge's actions

Nudge's buttons use dedicated endpoints instead of the UI rewriting the whole state, so a click can never overwrite a concurrent edit and each action is one atomic change followed by a replan. This supersedes the earlier "saves with PUT" wording in the Nudge section.

- `POST /api/soft/approve` `{ today, nowMinutes?, horizonDays?, date }`: adds `date` to `approvedSoft` (idempotent; a past date is a 400).
- `POST /api/soft/undo` (same body): removes `date`.
- `POST /api/warnings/dismiss` `{ today, nowMinutes?, horizonDays?, key }`: adds the warning key to `dismissed`.
- Each answers `{ blocks, warnings, approvedSoft, dismissed }`; every warning carries `key` and `dismissed`. `POST /api/replan` answers the same shape.
- **Approve** accepts only a date from today up to 60 days ahead that falls on a weekday with a soft window (otherwise 400). **Dismiss** answers 409 when the key does not match a currently open warning, so the UI can refresh and say "that warning changed".
- **Warning keys** identify what a warning is about (kind plus task, deadline kind, due date, week or date), not its wording. The minutes in a message change as the day goes on, so a dismissal survives that and is forgotten only when the shortfall disappears. This replaces the earlier `<kind>|<message>` rule.
- **Offers state their cost.** An offer's `detail.costMinutes` is how many more minutes other (non-study) tasks end up short if the date is approved; when it is above zero the message says so ("..., but other tasks lose 20 min") and Nudge must show it.
- **Static files:** dotfiles and any path segment starting with a dot are never served. The Content-Security-Policy also sets `base-uri 'none'` and `form-action 'self'`. It blocks inline `<style>` and `style="..."` attributes (setting `element.style` from script is allowed), so the UI must use stylesheets and classes.

## Planner changes needed by Nudge

Nudge's promise on the board is "I would only touch it for study, and only if you say so." Today the planner opens soft time on its own as a last resort. The UI needs an **ask** mode.

- **Preference `softMode`: `"ask" | "auto"`**, default `"ask"`. `"auto"` keeps today's behavior exactly. In `"ask"` mode the planner never opens a soft window by itself.
- **State field `approvedSoft: DateStr[]`**: soft-window dates the user approved. The planner treats those dates as opened, in either mode. Dates before today are dropped on replan.
- **Offers.** In `"ask"` mode, when a study shortfall remains, the planner finds the unopened soft date whose opening reduces the study shortfall the most (earliest wins a tie) and emits a warning of kind `soft-offer`, with `detail.date` and `detail.minutes` (the minutes it would recover). If no soft date helps, no offer is made and the shortfall stays a plain warning.
- **Structured warnings.** `Warning` gains an optional `detail` object: `{ taskTitle, kind, dueDate, minutes, date }` as applicable (kind is the deadline kind, such as `exam`). `message` is unchanged, so the CLI and tests keep reading plain text. Existing tests that compare whole warning objects are updated deliberately to include `detail`.
- **State field `dismissed: string[]`**: keys of warnings the user chose to leave (`<kind>|<message>`). A dismissed warning no longer counts toward the badge. Because the key includes the message, a changed shortfall is a new warning and reappears. Keys no longer matching any current warning are pruned on replan.
- Validation is extended for `softMode`, `approvedSoft` (real dates, at most 400) and `dismissed` (strings of at most 300 characters, at most 400).

## Behavior

### Week screen
- Opens on the current week. Arrows move by seven days. Blocks and commitments come from `state.blocks` and the commitment occurrences for each date. Past days are shown as they were.
- "N needs you" counts open warnings (not dismissed). Clicking it focuses Nudge.
- A filter hides blocks of its group and dims its row; counts always show the full week. At least one filter must stay on.
- Days show blocks in time order with the category label, time range and title. Overlaps cannot occur because the planner never produces them.

### Nudge
- **States:** *quiet* (no open warnings: just the character and "All clear" in mono), *speaking* (open warnings: badge shows the count, eyes shifted toward the message, the most urgent warning shown), *offline* (API unreachable: a plain message and a Retry button).
- **A warning bubble** shows: a headline built from `detail` ("Chemistry exam, Fri 23 Oct, is 90 min short."), and, when an offer exists, the line "Friday evening is free. I would only touch it for study, and only if you say so." with two buttons.
  - **Use Friday evening** (the weekday name comes from `detail.date`) appends the date to `approvedSoft`, saves, replans, and redraws. If the replan does not recover the minutes, Nudge says so plainly.
  - **After a yes**, Nudge confirms ("Done. Friday evening is in your plan." with the minutes recovered) with **Okay** and **Undo**. Undo removes the date from `approvedSoft`, saves, replans and redraws, so an approval is never a one-way door.
  - **Leave it** appends the warning key to `dismissed`, saves, and redraws.
- With several warnings Nudge shows one at a time, most urgent first (deadline shortfalls by due date, then weekly shortfalls), with "1 of N" and next/previous.
- **"Ask me" field:** visible, focusable, and honest. Submitting shows "I can't answer questions yet. That arrives with the AI phase." The text is not sent anywhere.
- **System notifications:** off by default. A single "Allow notifications" button asks the browser for permission. If granted, a notification is shown when a new, undismissed warning appears while the tab is hidden. No service worker, nothing when the app is closed.

### Setup
- Every list has an **Add** button, inline editing, and a **Delete** with a confirmation. Forms use real labels and inputs. Time entry is `HH:MM`; dates use the date input. Weekday choice is seven toggle buttons.
- **Save** sends the whole state with `PUT /api/state`, then replans. A validation error from the API is shown next to the form in vermilion with the API's field path (for example `tasks[0].maxBlock must be a number between 5 and 1440`) and nothing is lost from the form.
- Changing an id-bearing item keeps ids stable; deleting a task also deletes its deadlines (after confirmation that says so).

### Replan
- The button calls `POST /api/replan` with today's date and the current time in minutes, then redraws. While running it shows a busy state and ignores repeat clicks. Errors appear in Nudge's offline or warning state, never as a silent failure.

## Errors and empty states
- API unreachable, corrupt data file (500), or validation error: shown in plain language in the same bold style, with the file path for a corrupt data file, never a blank screen.
- Empty state: no commitments or tasks yet gives one headline, one sentence, and two buttons: Load the example, Add a commitment.
- A week with no blocks shows each day as "Nothing planned" in muted mono.

## Accessibility
- Real `button`, `a`, `input` and `label` elements; no click handlers on non-interactive elements. Visible focus ring (2 px ink, 2 px offset). Keyboard: Tab order follows the visual order; left and right arrows change week when the week header has focus.
- Text contrast of at least 4.5:1 (ink on paper, ink on vermilion, white on cobalt, ink on mustard all pass; muted text is used for secondary information only and is at least 4.5:1 on paper).
- Category is conveyed by label and by lightness, never by hue alone. Nudge has an accessible name and the bubble is an `aria-live="polite"` region.
- Respects `prefers-reduced-motion`: no animation of blocks or Nudge when set. By default motion is limited to short opacity and position transitions on filters and the bubble.

## Testing
- **Planner and API** (node:test, as now): ask mode, approved dates, offers, structured warnings, `dismissed` handling, validation of the new fields, static file serving (including a path-traversal attempt such as `/../package.json` and an encoded variant, which must be refused), security headers, `/api/example`.
- **View-model** (`js/model.js` is plain functions, tested under node:test): grouping by day across week and year boundaries, ISO week number (for example 2026-10-12 is week 42, 2027-01-01 is week 53 of 2026), totals, filter counts, category-to-group mapping with unknown categories, Nudge headline and offer text from `detail`.
- **Rendering** is intentionally thin and is checked visually against board D. There is no browser available in the development environment, so the user checks the rendered pages against the board and reports differences; this is stated plainly rather than claimed as verified.

They are not final until approved.
